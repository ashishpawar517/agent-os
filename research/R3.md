# Terminal Emulation and PTY in a Desktop/Web Context

## Overview
For a terminal-like UI in a desktop application, we need to emulate a pseudoterminal (PTY) that can:
1. Run shells and command-line programs
2. Handle input/output streaming
3. Support terminal features (colors, cursor control, resizing)
4. Integrate with a web-based frontend (like xterm.js)

## Solution: xterm.js + Backend PTY Library

### Frontend: xterm.js
- **Purpose**: Embed a full-featured terminal in a web context
- **Key Features**:
  - Zero dependencies (self-contained core)
  - Rich Unicode support
  - Performant rendering
  - Accessible (screen reader mode, contrast ratio)
  - Extensible via addons
- **API**:
  ```javascript
  import { Terminal } from '@xterm/xterm';
  const term = new Terminal();
  term.open(document.getElementById('terminal'));
  term.write('Hello from \\x1B[1;3;31mxterm.js\\x1B[0m $ ');
  ```

### Backend PTY Options

#### 1. Node.js + node-pty
- **How it works**: Uses `forkpty(3)` to spawn processes with pseudoterminals
- **API**:
  ```javascript
  const pty = require('node-pty');
  const shell = pty.spawn(process.platform === 'win32' ? 'cmd.exe' : 'bash', [], {
    name: 'xterm-color',
    cols: 80,
    rows: 30,
    cwd: process.env.HOME,
    env: process.env
  });
  
  // Data from PTY -> send to frontend
  shell.on('data', function(data) {
    // Send data to browser via WebSocket or similar
  });
  
  // Input from frontend -> write to PTY
  shell.write(data);
  ```
- **Features**:
  - Cross-platform (Linux, macOS, Windows 10+)
  - Resize capability
  - Flow control
  - Inherits parent process permissions
- **Limitations**: Not thread-safe

#### 2. Bun.spawn() with PTY support
- **How it works**: Built-in PTY allocation via `{ terminal: { ... } }` option
- **API**:
  ```typescript
  import { spawn } from "bun";
  
  const proc = Bun.spawn(["bash"], {
    terminal: {
      cols: 80,
      rows: 24,
      data(terminal, data) {
        // Forward child's output to parent
        process.stdout.write(data);
        // In desktop app: send to frontend via IPC/WebSocket
      },
      exit(terminal, exitCode, signal) {
        console.log("PTY closed, exitCode=", exitCode, "signal=", signal);
      },
    },
  });
  
  // Write to child's stdin via PTY
  proc.terminal.write("echo hello\\n");
  
  // Resize terminal
  proc.terminal.resize(100, 40);
  
  await proc.exited;
  proc.terminal.close();
  ```
- **Features**:
  - Cross-platform PTY (Unix: openpty, Windows: ConPTY)
  - Full duplex communication
  - Terminal features: TTY detection, ANSI colors, cursor control, resizing, raw mode
  - Reusable Terminal object
  - No extra dependencies
- **Platform Notes**:
  - **Unix/Linux/macOS**: Traditional PTY via `openpty()`
  - **Windows**: ConPTY (`CreatePseudoConsole`)
    - `\r` handling differs (passed through vs translated to `\n`)
    - SIGWINCH behavior limited
    - Close behavior may block on older Windows

#### 3. Deno
- **PTY Support**: Available via `Deno.run({ stdout: "piped", stderr: "piped" })` but not true PTY
- **Limitation**: No built-in PTY module in standard library as of v1.42
- **Workaround**: Use third-party packages or FFI to access system PTY functions

## Connection Pattern for Desktop App

In a Tauri/TypeScript desktop app:

1. **Frontend** (WebView):
   - Display xterm.js terminal in UI
   - Handle user keystrokes
   - Send input to backend via Tauri command/event system

2. **Backend** (Rust/Tauri):
   - Spawn shell process with PTY using Node.js child process (via Tauri's command system) 
   - OR spawn directly in Rust using `pty` crate
   - OR use Bun runtime via Tauri
   - Bridge PTY data to/from frontend
   - Handle resizing events

3. **Communication**:
   - Frontend → Backend: User input (keystrokes, paste, resize)
   - Backend → Frontend: Terminal output (data events)
   - Bidirectional via Tauri's command/event system

## Recommended Approach for Agent OS

**Bun.spawn() with PTY support** is ideal because:
1. **Built-in**: No extra dependencies needed
2. **Cross-platform**: Consistent API across Linux/macOS/Windows
3. **Feature-rich**: Full terminal emulation with resize, raw mode, etc.
4. **TypeScript-first**: Excellent TS support matches agent-os preference
5. **Performance**: Bun is fast and efficient
6. **Integration**: Easy to call from Tauri via command system

## Trade-offs and Considerations

### Capability
- **Pros**: Full terminal compatibility (shells, CLI tools, editors like vim/nano)
- **Cons**: No direct access to Chrome DevTools Protocol (unlike Chromium engine)

### Packaging
- **Pros**: Smaller than Electron (uses system webview via Tauri)
- **Cons**: Bun runtime adds some size (~4-5MB compressed) but still much smaller than Electron

### Login/Extension Fidelity
- Since it's a real PTY, shells behave exactly as they would in a real terminal
- Environment variables, working directory, signal handling all work correctly
- No limitations compared to native terminal emulators

### Streaming Implications
- Data flows bidirectionally via PTY
- Backend must pump data from PTY to frontend in real-time
- Frontend must render incoming data efficiently (xterm.js is optimized for this)
- Resize events need to be propagated to PTY
